# A股复盘系统第一阶段：数据库与 Dashboard 设计

## 1. 目标与边界

第一阶段把 ChatGPT 产出的标准化每日复盘 JSON 保存为可追溯的历史数据，并通过本地 Streamlit Dashboard 提供市场、主线、个股、驱动力、生命周期、证据和次日验证查询。

系统分工保持不变：ChatGPT 负责研究、归因和评分，本项目只负责校验、存储、比较和展示。`prompts/SYSTEM_PROMPT.md` 中的 41 类上涨驱动力和 `config/scoring.json` 中的 100 分公式是唯一业务基准，本阶段不重新设计评分体系。

本阶段不接实时行情，不开发分钟级交易系统、涨停预测、自动下单、模型训练、复杂账户系统或云部署。

## 2. 已确认的技术方案

- Python 应用采用 SQLAlchemy、Pydantic 和 Streamlit 多页面架构。
- SQLite 是历史查询库，原始 JSON 同时归档，保证可审计和可重放。
- Dashboard 采用密集工作台：首页优先展示市场状态、主线 TOP5、历史变化、次日验证和数据缺口。
- 真实数据采用严格模式。证据不足的评分保持 `null` 并显示“暂不评分”，不得猜测或以零代替。
- 10 个模拟交易日用于功能演示；2026-09-01 作为真实严格模式记录。两类数据默认隔离。

## 3. 架构与模块边界

### 3.1 输入与校验

`schemas` 和 Pydantic 模型共同定义标准 JSON 契约。Pydantic 是运行时权威校验器，JSON Schema 用于文档和外部工具校验。两者由同一组字段和枚举约束维护，并通过契约测试防止漂移。

校验错误必须输出精确 JSON 路径、收到的值和失败原因，例如：

```text
main_themes.1.stage: 非法生命周期“加速期”；允许值为朦胧期、发酵期、验证期、主升期、扩散期、兑现期
```

### 3.2 服务层

- `import_service`：协调读取、校验、归一化、比较、事务写入和归档。
- `theme_normalizer`：把题材别名映射到标准名称；未知名称可建立新题材，但不会自动猜测别名关系。
- `comparison_service`：查找同一 `data_kind` 的上一交易日，计算评分和阶段变化。
- `tomorrow_check_service`：新增验证条件，并由后续复盘更新历史条件状态。
- `query_service`：为 Dashboard 提供稳定的只读查询，页面不散落原始 SQL。

### 3.3 展示层

`app.py` 是 Streamlit 入口；各页面只依赖查询服务，不直接写数据库。页面共享日期、数据类型和题材筛选状态。

## 4. 标准 JSON 契约

顶层结构保留现有 `date`、`market_regime`、`main_themes`、`stocks` 和 `changes_vs_previous_day`，并增加：

- `schema_version`：输入契约版本。
- `data_kind`：`real` 或 `demo`。
- `strict_mode`：真实记录固定为 `true`。
- `completeness`：0 至 100 的数据完整度及缺失项列表。
- 市场宽度字段：成交额变化、涨跌家数、涨跌停数、最高连板高度和建议仓位区间。
- `evidence`、`risk_events` 和 `tomorrow_checks`。

每条主线保存规范名称、排名、生命周期、变化状态、因果链、驱动力、六个评分分项、三个展示评价、总分、评级和变化原因。每只核心股票保存代码、名称、题材、五类市场地位、可选地位说明、驱动力、催化、受益路径、因果链、评价、评级和生命周期。

### 4.1 严格空值规则

- 每个评分字段可以独立为 `null`，但必须在 `missing_reasons` 中记录对应原因。
- 只有固定公式所需的六个分项全部存在时，才允许生成主线 `total_score` 和 `rating`。
- 部分已知分项可以展示，但不得据此伪造综合分。
- 未核验的 D 级信息可以入库和展示，不得单独支撑高兑现分或强结论。
- 数据库中的 `0` 表示经过判断后的零分，不表示缺失。

### 4.2 业务一致性规则

- 评分分项必须落在 `config/scoring.json` 的范围内。
- 总分必须与固定公式一致，评级必须与总分区间一致。
- 驱动力代码和名称必须属于固定 41 项且互相匹配。
- 生命周期、变化状态、证据等级、个股地位和验证状态必须使用固定枚举。
- 股票代码必须符合沪深京 A 股代码格式；交易所可由代码规则推导并校验。

## 5. 数据库设计

### 5.1 导入与交易日

`review_import` 保存源文件路径、SHA256、原始归档路径、输入日期、数据类型、导入状态、错误明细和时间。失败导入也保留审计记录，但不会产生部分业务数据。

`trading_day` 使用代理主键，并对 `(trade_date, data_kind)` 建唯一约束。这样同一天可以同时保留演示版和真实版，而同日期、同类型的重复导入会被拒绝。表中增加 `strict_mode`、完整度、缺失项、建议仓位上下限和导入记录外键。

所有每日明细表通过 `trading_day_id` 关联交易日，避免仅凭日期把真实数据和模拟数据混合。

### 5.2 题材与评分

- `theme`：标准题材名称。
- `theme_alias`：明确维护别名到标准题材的映射。
- `theme_daily_score`：排名、生命周期、变化状态、因果链、六维评分、三项展示评价、总分、评级、缺失原因、`delta_score` 和 `delta_reason`。
- `theme_driver`：主线命中的固定驱动力及证据等级。
- `theme_relationship`：主线的上下游、映射、补涨和竞争关系。

`delta_score` 仅在当前日和同类型前一日都存在有效总分时计算，否则为 `null`；新增、暂不评分或前日缺失必须写明 `delta_reason`。

### 5.3 个股、证据和验证

- `stock`：代码、名称和交易所主数据。
- `stock_daily_score`：题材、市场地位、可选地位说明、生命周期、催化、受益路径、因果链、评价、评级、缺失原因和变化字段。
- `stock_driver`：个股关联的固定驱动力，补足现有 Schema 的缺口。
- `evidence`：实体、等级、类型、标题、来源、URL、发布时间、摘要和核验状态。
- `risk_event`：风险类型、级别、扣分、描述和证伪条件。
- `tomorrow_check`：提出日、关联实体、验证内容、状态、实际解决日和结果。

`tomorrow_check.status` 仅允许 `pending`、`confirmed`、`weakened`、`invalidated`。更新状态保留原提出日和原描述，不覆盖历史判断。

## 6. 导入流程与错误处理

命令保持为：

```powershell
python import_daily_review.py data/json/2026-09-01.json
```

处理顺序固定为：

1. 读取文件并计算 SHA256，将原文写入内容寻址归档；归档失败立即终止。
2. 建立独立的导入审计记录，使用 Pydantic 校验字段、枚举、代码、空值和评分一致性。
3. 归一化题材别名、股票代码和交易所。
4. 检查 `(trade_date, data_kind)` 是否重复。
5. 查找同类型上一交易日，计算 `delta_score`、阶段变化和变化原因。
6. 在单个数据库事务中写入交易日、题材、股票、驱动力、证据、风险和验证条件，并把导入审计状态更新为成功。
7. 校验或业务写入失败时，把审计状态和结构化错误更新为失败；已归档原文保留用于排错和重放。

任何业务写入失败都回滚整日事务。命令返回非零退出码，并输出错误路径和原因。默认不提供静默覆盖；未来如需修订历史数据，另行设计显式版本化流程。

## 7. Dashboard 信息架构

### 7.1 密集工作台首页

顶部提供日期和 `real/demo` 类型筛选，并显示数据标签和完整度。首屏依次展示：

- 市场状态、成交额及变化、涨跌家数、涨跌停数、最高板和建议仓位。
- 主线 TOP5 表格：评分、评级、昨日分数、变化、生命周期、状态、龙头、中军和补涨。
- 可切换评分维度的主线历史走势图。
- 次日验证状态汇总和真实记录缺失项。

真实与模拟数据默认不混合统计。所有空值显示“暂不评分”或“数据不足”，同时可以查看缺失原因。

### 7.2 多页面

- 主线详情：因果链、评分拆解、核心股票和逐日变化原因。
- 核心个股：按名称或代码搜索，展示地位、受益路径和历史评价。
- 上涨驱动力统计：固定 41 项在可选时间窗口内的出现次数、平均有效评分和 S/A 级次数。
- 生命周期统计：主线阶段分布和历史转移；第一阶段不做收益率预测。
- Evidence Center：按日期、等级、验证状态、题材和股票筛选，保留原始链接。

无数据库、无交易日、无匹配题材或股票时，页面显示明确空状态，不抛出堆栈或渲染空白。

## 8. 测试设计

### 8.1 契约与业务规则

覆盖缺失字段、非法评分、非法生命周期、非法评级、非法股票代码、非法驱动力、公式不一致、严格空值缺少原因，以及 JSON Schema 与 Pydantic 契约一致性。

### 8.2 数据库与服务

覆盖新交易日、重复日期和类型、新题材、新股票、题材别名、事务回滚、评分上涨、评分下降、首次出现、主线证伪、同类型前日比较和 `tomorrow_check` 状态更新。

### 8.3 Dashboard

通过查询服务测试并进行关键页面启动检查，覆盖首页、主线详情、个股搜索、驱动力、生命周期、证据中心、空数据库、无匹配结果、真实/模拟切换和严格空值显示。

## 9. 测试数据

生成至少 10 个模拟交易日，覆盖 AI 算力、机器人、固态电池、创新药和化工涨价。数据变化由明确事件和生命周期演变驱动，不使用无解释随机数。至少包含上涨、下降、首次出现、扩散、兑现和证伪场景。

2026-09-01 真实记录使用已有市场、题材和涨停梯队资料导入。无法由可靠证据支持的分项保持 `null`，并记录缺失原因。演示数据和真实数据通过 `data_kind` 及 `trading_day_id` 全链路隔离。

## 10. 完成标准

全新环境中必须实际执行并通过：

```powershell
pip install -r requirements.txt
python scripts/seed_demo_data.py
python import_daily_review.py data/json/2026-09-01.json
pytest
streamlit run app.py
```

验收要求：

- 数据库包含 10 个逻辑连贯的模拟交易日和一份 2026-09-01 真实严格记录。
- 所有规定页面可访问，密集工作台与已确认原型一致。
- 模拟和真实数据不会混算；评分缺失不会被伪造。
- 用户任务列出的 12 类测试全部覆盖，新增的事务、隔离和契约测试通过。
- README 提供经过验证的安装、导入、测试和启动命令，并说明当前数据类型。
- 实现过程按数据库、Schema、导入器、演示数据、Dashboard、测试、运行修复和 README 的顺序逐阶段验证。

## 11. 实施约束

实现应保持模块小而明确，沿用现有目录和业务配置，只对当前目标所需结构做调整。数据库结构由 SQLAlchemy 模型管理，并同步维护可直接初始化 SQLite 的 `sql/schema.sql`。不引入迁移框架、认证系统、任务队列或额外前端框架。
